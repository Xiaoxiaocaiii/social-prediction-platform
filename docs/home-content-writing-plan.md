# 首页四章节内容编写方案

## 1. 编写目标

本方案用于指导首页四个独立章节的文字充实与后续审核。内容面向大创答辩评审、软件著作权材料审阅者和首次使用平台的非技术用户，要求同时满足：

- 通俗：首次阅读即可理解“平台在做什么、为什么这样做、结果如何验证”。
- 专业：准确说明 SMTPD 数据、BM25/FTS5 检索、Day1-Day30 时序和当前基线预测逻辑。
- 可追溯：所有数字、结论和案例描述都必须来自真实数据或现有接口契约。
- 可复用：四章使用同一套标题、正文、注释和信息卡片规范。

本轮只充实文字和信息表达，不修改后端、接口、预测算法、SQLite 数据或图表原始数据。

## 2. 四章节主题与内容边界

| 章节 | 核心主题 | 必须回答的问题 | 内容出口 |
| --- | --- | --- | --- |
| 01 数据基础 | 一条视频样本由文本、封面和 30 天序列共同构成 | 平台分析的对象是什么？为什么不能只看一张榜单？ | 可检索的真实样本 |
| 02 检索增强 | 先从真实历史内容中找到可解释的参考集合 | 用户输入如何找到相似案例？参考案例凭什么可信？ | 可回看的参考集合 |
| 03 时序预测 | 用统一 Day1-Day30 位置观察热度变化 | 平台如何从离散曲线提炼趋势指标？ | 可解释的预测路径 |
| 04 真实案例 | 每个结论都回到具体视频和原始曲线 | 用户如何验证结论，而不是只接受一个数字？ | 可回到证据源 |

### 2.1 第一章：数据基础

叙事顺序固定为：

1. 先说明平台不是只展示排行榜，而是围绕同一视频组织多模态数据。
2. 解释三类数据的角色：
   - 文本：标题、标签、描述，用于理解选题并支持检索。
   - 封面：保留视频的视觉线索，支持结果回看。
   - 热度序列：统一记录 Day1 到 Day30 的变化。
3. 使用真实规模 `282,481`、`15`、`30` 说明数据范围，不延伸出未经计算的新指标。
4. 结尾明确输出：用户得到的是“可检索的真实样本”，不是静态榜单截图。

禁止写法：把三类数据描述成已经完成的视觉模型、语义模型或预测模型；当前项目没有这些事实依据。

### 2.2 第二章：检索增强

叙事顺序固定为：

1. 先说明用户输入的是一个研究选题或文案。
2. 再说明平台从标题、标签、描述等真实文本字段中寻找相似内容。
3. 首次出现时解释 `BM25 / FTS5`：
   - FTS5：本地全文检索索引。
   - BM25：按文本相关度排序的检索方法。
4. 说明短文本或异常查询会使用现有 LIKE 兜底，不把检索描述成“理解用户意图的智能模型”。
5. 说明参考集合保留标题、分类和完整热度曲线，便于后续回看。

禁止写法：声称检索结果代表“最准确答案”、声称使用了语义向量模型，或暗示图片已经参与当前检索。

### 2.3 第三章：时序预测

叙事顺序固定为：

1. 说明所有参考视频都被放到统一的 Day1-Day30 时间位置上。
2. 说明基线曲线由参考案例真实曲线逐日平均得到。
3. 解释三个指标：
   - 峰值天：30 天中热度最高的位置。
   - Day30：第 30 天的热度位置。
   - 衰减率：从 Day1 到 Day30 的相对变化，用于观察热度保持情况。
4. 明确当前是“基线预测路径”，不是已经训练完成的深度学习模型。
5. 结尾强调：指标用于解释参考案例的共同趋势，不等同于预测准确率。

禁止写法：新增准确率、召回率、模型排名或训练结果；不得把平均曲线写成未来真实走势的保证。

### 2.4 第四章：真实案例

叙事顺序固定为：

1. 先说明预测和洞察必须回到具体视频验证。
2. 说明案例详情可回看标题、分类、Day30、峰值天和完整 30 天曲线。
3. 通过三个正式页面建立验证路径：
   - 排行榜：筛选真实视频。
   - 数据洞察：查看整体规律。
   - 曲线对比：验证个体差异。
4. 结尾强调平台输出的是“可追溯证据链”，不是脱离数据源的结论。

禁止写法：添加没有真实接口支撑的作者信息、播放量增长、点赞率、预测准确度或视频内容评价。

## 3. 单章节文字结构

每个章节统一使用以下结构：

1. **章节眉标**：`01 · DATA FOUNDATION` 形式，说明章节编号和英文主题。
2. **一级大标题**：一句话提炼本章核心结论，必须加粗。
3. **导语正文**：用 1 段话回答本章“依据、作用、输出”，不超过 80 个汉字为宜。
4. **解释模块**：2~3 个短段或信息卡片，每块只表达一个概念。
5. **证据标签**：用 `BASIS / ROLE / OUTPUT` 标识依据、作用和输出。
6. **章节收束句**：把本章输出自然连接到下一章，避免重复标题。

文字优先采用“先结论、后解释、再限定”的顺序。每个段落最多包含一个专业判断和一个限定条件。

## 4. 术语通俗转化方法

所有专业术语按照“五步法”处理：

1. **先给通俗动作**：例如“从历史视频里找到相似参考”。
2. **首次出现再给术语**：例如“平台使用本地全文检索（FTS5）”。
3. **补充术语作用**：说明它解决的是“从哪些文本字段找到参考”。
4. **绑定真实场景**：使用用户输入选题、标题、标签、描述或 Day1-Day30 曲线作为例子。
5. **补充边界**：说明短文本会走 LIKE 兜底、图片当前不参与预测、基线结果不代表准确率。

统一转化示例：

| 专业表达 | 页面推荐表达 |
| --- | --- |
| FTS5 trigram | 本地全文检索索引，用来从标题、标签和描述中找相似文本 |
| BM25 | 按文本相关度给候选案例排序的方法 |
| 逐日平均 | 把多个视频同一天的位置放在一起计算平均值 |
| 峰值天 | 30 天热度序列中达到最高的位置 |
| 衰减率 | 用 Day1 和 Day30 的变化观察热度保持情况 |
| baseline | 当前用于演示和解释的基线预测路径，不等于训练完成的模型 |

禁止使用没有解释的缩写堆叠；同一术语在全文中只能采用一种中文译法。

## 5. 全格式标准

### 5.1 字体、字号和行距

| 文本角色 | 字体 | 字号 | 字重 | 行高 | 用途 |
| --- | --- | ---: | ---: | ---: | --- |
| 一级大标题 | `Noto Serif SC`，本地等效衬线字体 | 38px | 700 | 1.25 | 每章核心标题，必须加粗 |
| 章节眉标 | `Inter` / `IBM Plex Mono` | 11px | 700 | 1.4 | 编号、英文主题 |
| 正文导语 | `Noto Sans SC` / `Microsoft YaHei UI` | 16px | 400 | 1.72 | 解释依据、作用和输出 |
| 二级小标题 | `Microsoft YaHei UI` / `Noto Sans SC` | 18px | 650 | 1.45 | 信息卡片标题、步骤标题 |
| 注释说明 | `Noto Sans SC` / `Microsoft YaHei UI` | 12px | 400 | 1.55 | 边界、口径、补充说明 |
| 数据数字 | `Inter` / `IBM Plex Mono` | 29px | 600 | 1.2 | 真实规模和指标 |
| 数据标签 | `IBM Plex Mono` | 10px | 400 | 1.4 | `BASIS / ROLE / OUTPUT` |

一级大标题不得使用圆体或手写体；正文、二级标题、注释必须与一级大标题形成明显字体区分。全章节禁止使用外部字体 CDN。

### 5.2 标点和段落

- 中文正文使用全角标点；英文缩写、数字和单位之间保留必要空格。
- 一段只承担一个语义任务，正文段落建议 2~4 句。
- 不使用“非常智能”“精准预测”“显著提升”等无法由真实数据证明的宣传词。
- 所有真实数字保留项目现有口径：`282,481`、`15`、`30`，不自行四舍五入或改写。
- 章节标题采用陈述句或判断句，不使用空泛口号。

## 6. 多媒体元素排版

多媒体元素不再强制统一放在右侧，而是根据内容类型选择最清晰、最平衡的布局。统一要求是：模块必须服务于本章主题，不能遮挡正文，也不能超出独立章节的可视范围。

- 文字、图片、曲线、数据卡、流程卡和案例卡均采用独立模块，不环绕正文。
- 章节内容区域使用 `100%` 可用宽度，具体列数和占比按内容密度调整；同类模块保持相同的卡片结构、边距和间距。
- 模块与正文之间通常保留 `20px~36px` 间距，章节边界至少保留 `28px` 内边距。
- 横向流程或方法卡优先使用三列并排；案例与验证内容优先使用两列并排；信息密度较高时可改为正文下方横向布局。
- 任何布局都必须为章节底部保留约 `85px` 留白，不得为了对齐强行拉伸卡片或把内容挤到页面底部。

四章布局建议：

| 章节 | 推荐布局 |
| --- | --- |
| 数据基础 | 左侧说明与右侧案例证据卡并列 |
| 检索增强 | 正文下方三步横向流程卡 |
| 时序预测 | 正文下方三列指标方法卡 |
| 真实案例 | 真实视频案例卡与继续验证路径卡两列并排 |

所有装饰性背景元素继续保持 `pointer-events: none`，不得遮挡文字、焦点或右侧证据模块。

## 7. 内容打磨执行流程

### 阶段一：事实盘点

1. 对照 `README.md`、交接文档和现有接口，列出可使用的真实数字、术语和业务动作。
2. 标记不可写内容：mock 数据、预测准确率、未实现的图片预测、未接入的模型能力。
3. 为每章建立“主题句—依据—作用—输出”四格表。

### 阶段二：初稿编写

1. 按四章节主题分别编写眉标、一级大标题、导语、信息卡文案和收束句。
2. 先写通俗表达，再补专业术语和边界。
3. 控制每个卡片只讲一个概念，避免把算法、数据和结论挤在同一句话里。

### 阶段三：专业复核

1. 检查术语是否与现有实现一致。
2. 检查每一个数字是否能追溯到 README、接口或数据库字段。
3. 检查是否把基线算法写成训练模型，是否把相关性写成因果关系。
4. 检查检索、预测、洞察和案例验证之间的因果顺序。

### 阶段四：版式适配

1. 按章节内容类型选择并列、横向流程或两列案例布局。
2. 检查四个章节眉标、一级标题、正文起点和模块基准线是否对齐。
3. 检查长标题、中文断行、英文缩写和数字不被裁剪。
4. 检查键盘焦点、对比度和 `prefers-reduced-motion` 下的可读性。

### 阶段五：浏览器验收

在桌面 Edge 的 `1920×1080`、`2560×1440`、`3840×2160` 下逐章检查：

- 章节链接和“研究路径”是否把目标章节定位到固定导航下方；
- 四章一级标题是否加粗且位置统一；
- 四章正文起点和右侧证据模块是否统一；
- 没有横向溢出、裁剪、遮挡或内容错位；
- 控制台无错误，现有业务导航和真实数据行为不变。

## 8. 内容审核校验机制

### 8.1 事实校验

- [ ] 数字只使用真实数据或现有接口返回值。
- [ ] 不新增 mock 案例、虚构 KPI、准确率或模型结果。
- [ ] FTS5、BM25、LIKE、Day1-Day30、峰值天和衰减率的解释与实现一致。
- [ ] 不把相关性表述为因果关系。
- [ ] 不把基线平均曲线表述为真实未来走势保证。

### 8.2 表达校验

- [ ] 每章只有一个核心主题。
- [ ] 首次出现的专业术语有通俗解释。
- [ ] 每段文字能够回答“依据、作用或输出”中的一个问题。
- [ ] 标题、正文、二级标题和注释使用统一字体层级。
- [ ] 没有空泛宣传词、模糊主语或无法验证的绝对化表述。

### 8.3 版式校验

- [ ] 四个一级大标题全部加粗。
- [ ] 四个章节眉标位于统一基准线。
- [ ] 非纯文本模块的位置符合内容类型，且同类模块结构和间距一致。
- [ ] 所有模块未超出独立章节，并保留底部留白。
- [ ] Edge 桌面分辨率下无裁剪、溢出和遮挡。

## 9. 后续执行顺序

1. 先完成四章文字初稿和术语表。
2. 优先落地第一章“数据基础”，作为格式样板。
3. 用户确认第一章后，按同一模板编写第二至第四章。
4. 完成四章文字审核后，再进行统一排版和浏览器验收。
5. 仅在内容和版式均确认后，才考虑迁移到正式首页；本轮默认不迁移正式页面。
